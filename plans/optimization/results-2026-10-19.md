# Optimization results, 2026-10-19

What landed, how it was measured, and what is still open. Decisions taken
this session: D1-A (triage on demand), D2-A (documentation stays blocking; it
is skipped for library projects anyway), D3 no resident worker, D4 bench on
a separate disk, D5 verification-closure key.

## Method

- **Bench.** A disposable copy of the reference consumer (`.psx-bench-disposable`
  marker, separate disk), with its preprocessing receipts rebased to the copy's
  path. Every equivalence check ran against it, never against the live project.
- **A/B.** Harness A is the tree as it stood before this session (HEAD plus the
  uncommitted work at that time); B is the optimized tree. Both run the same
  entry points on the same bench state.
- **Replay.** `tools/testing/loopReplay.ts` drives the real `runLoop` with a
  scripted agent. It writes each target's recorded matching source, calls the
  real `psx_finalize_function` tool and ends its turn. The run covers four
  consecutive library matches plus one selection. There is no model in the
  loop, so the time measured is harness time only.
- **Counters.** `PSX_PERF_COUNTERS=<file>` (`tools/lib/perfCounters.ts`) makes
  every process append its work counts on exit. Production loops now also
  write `<runtimeDir>/timings.jsonl`, one record per function (§0.2).

## Regression found first

On 2026-10-18, `bb39664` added `libraryAssemblyInputs`, called for every stub
part, and a 2,164-entry `views.elf` map. That pushed harness time per function
from ~17.5 s (the 10-17 baseline) to ~215 s.

| Cause | Detail |
|---|---|
| `loadLibraryProject` | Unmemoized, so the 136 KB `project.json` was parsed and validated on every call, about 33,750 times per graph rebuild. `object(x, Object.keys(x))` was also quadratic and always true. |
| `executedToolIdentity` | Read the whole `cccp` binary on every call (7.4 GB of I/O per rebuild). |
| `validateElfView` | Ran `relocations.find` for every byte of every section. |

## Results

Standalone, on the bench, warm:

| Operation | A (before) | B (after) | Equivalence |
|---|---|---|---|
| Call-graph rebuild | 105–118 s | 3.2–3.9 s | byte-identical `callGraph.json` |
| Preparation (`m2cFunc`) | 93–99 s | 1.6–1.8 s | packets, `.i`, handoff and evidence identical across 6 targets, except the D1-A triage fields |
| Triage, now on demand | ~90 s | 4.2 s | findings and `macroIdentity` identical to A's inline run |

Whole loop, A/B on the same replay (four library matches and one selection):
1,145 s under A and 44.9 s under B. Both produced the same four matches. The
commits have identical subjects and identical trees, and the accepted records
and published context files are identical. The completion identities differ
only through `buildToolInputs`, which hashes harness implementation files by
design.

Loop replay, four library matches (B):

| Window per function, steady state | First B run | Final B |
|---|---|---|
| Loop re-verification after the agent's finalize | 5.7 s | ~1.0 s (in-process library receipt) |
| Agent `psx_finalize_function` | 4.2 s | 2.6 s (one child process instead of three) |
| Selection (graph) | 5.9 s | 1.6–2.0 s (graph prefetched as soon as machine verification passes) |
| Preparation | 1.6 s | 1.7 s |
| Fold attempt | 1.2 s | 0.1 s (in-process refusal) |
| `state.json` write | 0.5 s (110 MB) | 0.01 s (36 KB; input maps are content-addressed sidecars) |
| Total harness time per function | ~20 s | ~8.3 s |

## What landed, by phase

- **Regression fixes.**
  - `loadLibraryProject` keeps one deep-frozen configuration per text.
  - `object()` checks are O(n).
  - The ELF magic is read as 4 bytes.
  - `validateElfView` is linear.
  - `referenceHeaderCopy` is memoized per invocation.
  - Assembly-TU dependency scans go through the validated dependency cache.
  - Config text is re-read only when its stamp changes, within a scope.
- **Hashing.** `fileDigest` reuses a digest across scopes only for files whose
  ctime had settled for 2 s before the read (principle 2's ctime guard).
- **Inventory.** It is reused per accepted configuration while every input's
  real path and content digest recompute equal, and the parse's input checks
  re-run every time.
- **Phase 0.**
  - Counters.
  - Production `timings.jsonl`.
  - Synthetic library fixture (`tools/testing/libraryProjectFixture.ts`).
  - Budget tests (`tools/lib/perfBudgets.test.ts`).
  - Loop replay.
- **Phase 1.**
  - 1.1: in-process library receipt (`.pi/extensions/psx-decomp/tools/library-receipt.ts`),
    with negative controls in `library-receipt.test.ts`.
  - 1.2: one changed-files reading shared by policy and finalize.
  - 1.5: slim loop state.
- **Phase 2.**
  - 2.1/2.2: the verification key covers only the import closure of the
    verification entry points plus runtime data (`tools/lib/verificationClosure.ts`).
  - A completeness test runs a real member check and fails on any harness module
    or file it loads outside the closure.
- **Phase 3.**
  - 3.1: a failed rebuild uses the previous graph only for unchanged inputs.
  - 3.2: the graph rebuild is prefetched, abortable, and validated by
    graph-input identity at start, at end and at use.
  - 3.3: `withPreprocessorMetadata` around the verification batch, and
    `analyzeCSource` memoized by text.
- **Phase 4.**
  - D1-A: `macroIdentity` is computed inline, scoped to the target member.
  - The read-before-definition scan overlaps generation.
  - Library hashing goes through `fileDigest`.
- **Phase 5.**
  - The diff, member check and context export run in one child
    (`tools/agent/libraryFinalizeGate.ts`). Each step reports exactly what its
    CLI reported.
  - Publication is staged: it is rolled back unless the gate passes.

## Still open

- 2.3/2.4: per-member record writes and parallel re-verification. These matter
  less now that D5 limits mass re-verification to edits on the verification path.
- 3.4/3.5: persistent per-member caches and a precomputed next target. These
  would remove the remaining ~1.5 s selection wait.
- 4.4: packet fingerprint reuse (needs a prep-led ladder to matter).
- 5.2/5.4: one shared compile across diff, check and export, and a
  content-addressed compile cache.
- Phase 7: speculative preparation of the next function during the model's
  solve (~1.7 s per function); needs D3-compatible lifecycle handling.
